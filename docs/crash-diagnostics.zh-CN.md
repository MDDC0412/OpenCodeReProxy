# Windows 异常退出与日志排查

二开版在 Windows 双击启动时保留异常退出后的控制台，并默认将诊断信息写到磁盘。日志用于确认退出原因；增加诊断能力本身不代表已经修复尚未复现的故障。

## 本次排查结论

2026-10-10 用户报告原版 v1.3.7 在服务已经启动、正在处理请求时突然退出，未手动关闭窗口。参考程序的构建信息对应上游提交 `ef2df3f0562e2df7b64db94be8de636c54ab88ac`，使用 Go 1.24.13、Windows amd64、CGO 关闭。

原版目录没有持久运行日志或已发现的崩溃转储；Windows Application / WER / 资源耗尽记录中未找到匹配证据。已对照该确切提交检查请求、流式转换、后台模型探测与刷新、共享目录、代理池和退出路径，尚未复现用户报告的退出，因此不能确定它由 panic、Go 致命错误、资源耗尽或外部终止中的哪一种导致。

确认的诊断问题：

- 原版主要输出到控制台，WebUI 日志环也仅在内存中；窗口关闭后缺少证据。
- HTTP handler 的 recover 不能捕获其他 goroutine 的 panic，也不能恢复 Go 的致命错误。
- 原版在实际绑定端口前报告已监听；监听失败触发整体退出，却可能返回成功退出码。本次修复该行为，但它不能解释已经正常启动后的所有退出。

## 启动与窗口保留

将新版 `opencode2api.exe` 放在自己的配置目录中，继续使用已有 `config.json`。Windows 直接双击 exe 时，如果该进程独占新控制台，它会启动一个服务子进程并监控退出状态。

- 异常退出：保留窗口，显示捕获到的 panic / fatal 首行或配置、监听等错误，以及退出码和控制台记录位置。按回车才关闭。
- Ctrl+C 正常退出：记录信号和退出原因，不暂停。
- 普通 HTTP handler panic：仍返回服务端错误并记录堆栈；通常无需结束整个服务。
- 不会自动重新启动服务或重新提交中断的请求。窗口保留期间，服务已经停止。

从已有 PowerShell / cmd 或无控制台的服务环境启动时，默认直接运行服务。需要明确控制行为时使用：

```powershell
# 即使在已有终端里，也监控服务并在异常退出后等待回车
.\opencode2api.exe -config .\config.json -pause-on-error=always

# 自动化或外部服务管理器：异常退出立即返回退出码
.\opencode2api.exe -config .\config.json -pause-on-error=never

# 自定义诊断目录
.\opencode2api.exe -config .\config.json -log-dir .\diagnostics
```

控制台自动检测使用 Windows 的 `GetConsoleProcessList`。监控进程和服务进程共用一个控制台；内部子进程标记防止重复启动监控进程。监听 API / WebUI 端口的是服务子进程，可以通过启动记录中的 PID 和 parent PID 区分。

## 保存的文件

默认目录是实际配置文件旁的 `logs/`，不是固定为 exe 所在目录。每次启动按 UTC 时间和 PID 创建独立文件，重启保留旧记录。

| 文件                     | 内容                                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `runtime-时间-PID.log`   | JSON 运行日志，包括版本、Go 版本、程序路径、配置路径、请求开始 / 转发 / 结果、handler panic 堆栈、服务监听和退出原因。 |
| `crash-时间-PID.log`     | Go 原生的未处理 panic 与致命错误堆栈，覆盖后台 goroutine。只有启动头而没有堆栈表示没有捕获到 Go 崩溃报告。             |
| `console-时间-父PID.log` | 开启窗口保留时，由监控父进程保存子进程标准错误、关键生命周期 / 错误日志、子 PID、退出时间、退出码和最后记录的原因。    |

Go 的部分致命错误首行只发往标准错误，崩溃文件可能只包含堆栈；监控父进程同时保存完整标准错误，并在子进程退出后排空输出管道，再提示回车。

运行日志和控制台记录以 10 MiB 轮转，分别保留 `.1`、`.2`、`.3` 三份备份，单条日志不切断。原生崩溃文件独立保存。旧启动的文件不会自动清理，以免重启丢失故障证据；确认不再需要后可手动清理已停止进程的记录。

首选目录不可写时，尝试系统用户缓存目录下 `opencode2api/logs/配置路径指纹/`，并在启动输出中给出位置；两处都不可写时仍尝试运行服务，并输出诊断失败信息。

每分钟以及服务启停时记录 `process_health`：Go heap / sys 字节数、GC 次数、goroutine 数、正在处理的请求和流。它反映 Go 运行时状态，不等同于 Windows 的工作集或系统可用内存。生命周期与健康记录不受业务日志级别切换影响；请求开始 / 转发记录在 `info` 及以上详细级别可见，建议排查时保持 `logging.level=info`。

`trace_id` 将读取请求体前的开始事件与请求结果关联；`request_id` 将转发事件与上游尝试关联。无需开启 `logging.dump_request_bodies`。运行 JSON 日志沿用已配置敏感值的脱敏规则；原生崩溃和标准错误是原始诊断内容，可能含 panic 文本，分享前检查敏感值。

## 再次异常退出后

保留控制台，记录大致时间和当时调用的模型、入口协议、是否流式。发送对应启动的 `runtime-*`、`crash-*` 和存在时的 `console-*` 文件及轮转备份；无需发送含密钥的 `config.json`。

| 证据                                        | 能判断的情况                                                            |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| `request_panic` 及 `stack`                  | 被恢复的 HTTP handler 异常，可定位代码位置；它通常不会终止整个进程。    |
| `panic:` / `fatal error:` 及 goroutine 堆栈 | Go 未处理异常或致命错误，可继续定位具体调用和并发状态。                 |
| `server_failed`，`phase=listen`，退出码 1   | 配置端口占用或绑定失败，不是运行期间的推理异常。                        |
| `process_stopping`，`reason=signal`         | 服务收到了退出信号，随后正常关闭。                                      |
| 非零退出码但没有 Go 堆栈                    | 仍需结合 Windows 错误、资源耗尽或安全软件记录判断，不能只据此断言 OOM。 |

如果操作系统、任务管理器或安全软件终止了整个进程树，或用户关闭了控制台本身，程序无法保证保留窗口或写出退出后的记录。已有日志仍可用于判断终止前的状态。

## 回归验证

```powershell
go test -count=1 ./cmd/opencode2api ./internal/telemetry
go test -count=1 ./...
go vet ./...
```

回归使用隔离子进程模拟后台 panic、主协程 panic 和栈溢出的 Go 致命错误，检查崩溃堆栈、崩溃前的请求记录、父进程捕获的 fatal 首行和退出码。还覆盖回车等待、分段输出、缓冲上限、端口冲突、第二监听失败释放第一监听、异常关闭、正常信号、并发日志完整性、轮转、脱敏与输出失败时 WebUI 日志保留。模拟故障用于验证诊断机制，不是对用户原版退出根因的复现。
